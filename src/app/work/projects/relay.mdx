## The challenge

About 350 people at a logistics company send requests to four teams, and each request needs the right team, a clear reply and a record of what happened. The tool had to help the team without making decisions for it, and keep one company's data away from another's.

## What I did

1. **Wrote the requirements and user stories** for each sprint, with acceptance criteria as Given / When / Then scenarios that each one was tested against by hand.
2. **Set the rules before the screens.** Who may see, take, assign, close and reopen a request, and what a manager can change, were written as database rules, not only as buttons on a page.
3. **Built the AI parts to suggest and flag.** A classifier routes each request and marks low-confidence ones for a person to check. AI drafts are labelled, and an agent edits and sends them. Sensitive requests (harassment, self-harm, injury, security breaches) never go to the AI.
4. **Added the management side:** a dashboard, weekly reports with a PDF, a 28-day workload forecast, an audit log, flagged replies, a risk report and approvals for purchases and leave.
5. **Took it live** on Vercel with Supabase, and kept the main branch protected: every change went through a pull request, with a required review and checks.

## Built with

**Next.js 15** and **React** with **TypeScript**, styled with **Tailwind CSS** and shadcn/ui. **Supabase** holds the Postgres database, sign-in and row-level security on every table. The classifier is a TF-IDF and logistic regression model trained in **Google Colab** with scikit-learn, exported to JSON and run in TypeScript on the server, so no Python server runs in production. Drafts and summaries use the **Google Gemini API**, with the key kept on the server. Email notifications are built on **Resend** and are being switched on, and the site runs on **Vercel**.

## What I learned

The hard problems were never the AI. They were permissions and sequence. Live testing found a manager's list that showed people from every company, and a new invitee who reached the two-step sign-in before choosing a password. Both were fixed in the database and the sign-in flow, and both were the kind of problem that only shows up when you test as each role. Writing the rules down first, and testing them as each person, is the habit I now start every project with.
