## The problem

About 350 people at a logistics company send requests to four teams, and each request needs the right team, a clear reply and a record of what happened. The tool had to help the team without making decisions for it, and keep one company's data away from another's.

## I started with the rules, not the screens

Before building, I wrote the user stories with Given / When / Then acceptance criteria for each sprint, and each one was tested by hand. Then I wrote who may see, take, assign, close and reopen a request, and what a manager can change, as rules in the database. The screens depend on those rules, not the other way round.

## How it works

1. **Submit a request:** staff choose a subject, depot and urgency. A classifier routes it to a department. A fixed set of rules marks sensitive requests (harassment, self-harm, injury, security breaches), and those never go to the AI.
2. **Take and answer:** an agent takes the ticket, edits an AI draft in the tone they choose, and sends it. Drafts are labelled, and only the assigned agent can send a reply.
3. **Track it:** managers assign, confirm, close and reopen tickets, and staff see the status of each request in plain words.
4. **Watch the numbers:** a dashboard, weekly reports with a PDF and a workload forecast show what is happening in each department.
5. **Check the AI:** an audit log records every AI decision and every human change, with flagged replies and a risk report for compliance.

![Manager dashboard: ticket counts, average hours to first reply, and an AI summary written from the numbers](/images/projects/relay/dashboard.png)

## The features

- **Staff:** submit a request with a depot and urgency, then follow it under My requests.
- **Agents:** an inbox with a Mine filter, a ticket view and a template library.
- **Managers:** a dashboard, forecast, approvals for purchases and leave, reports and Manage users.
- **Compliance:** the audit log, flagged replies and the risk report.
- **Platform admins:** create companies, add each company's first system admin, and see each company's people, but never its tickets.

## Keeping companies apart

Relay started as one company's help desk and grew to eight companies on one system. The database rules keep each company's people and tickets apart for anyone who is signed in. An audit before the showcase found the gap those rules can't cover: jobs that run with nobody signed in, such as the Monday summaries and reports, automatic assignment and urgent escalation. Row rules don't apply to them, so they counted every company's tickets together and could have notified a manager in another company.

I wrote the fix as one reviewed migration. Every one of those jobs now checks the company itself, and reports and summaries are kept per company. I tested it on the demo database with a second company inside a transaction that was rolled back, so nothing was left behind. I also locked a demo-only reset function on the live database, because it would have cleared every company's open tickets.

## Built with

**Next.js 16** and **React** with **TypeScript**, styled with **Tailwind CSS** and shadcn/ui. **Supabase** holds the **PostgreSQL** database, sign-in and row-level security on every table. The classifier is a TF-IDF and logistic regression model trained in **Google Colab** with scikit-learn, exported to JSON and run in TypeScript on the server, so no Python server runs in production. Drafts and summaries use the **Google Gemini API**, with the key kept on the server. Email notifications are built on **Resend** and are being switched on, and the site runs on **Vercel**.

## What's next

Automatic assignment and urgent escalation are now live. Next: switch on email notifications, add backup codes for two-step sign-in, and let staff choose a request type on the form so purchases and leave go to a manager on their own.

## What I learned

The hard problems were never the AI. They were permissions and sequence. Live testing found a manager's list that showed people from every company, and a new invitee who reached the two-step sign-in before choosing a password. Both were fixed in the database and the sign-in flow, and both only showed up when I tested as each role. Writing the rules down first, and testing them as each person, is the habit I now start every project with.
