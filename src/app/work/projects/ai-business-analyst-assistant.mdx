## The problem

Business analysts spend hours turning short, vague requirements into user stories, acceptance criteria, test cases and stakeholder questions. AI can draft these in seconds, but left alone it fills gaps with plausible-sounding rules. **For a BA, an invented rule that looks real is worse than a gap that's flagged**, because it gets built.

## The approach: build around a prompt, not a model

I designed a **master prompt** that works like a job description for the assistant:

- **Role:** an assistant to the analyst, not a replacement. The analyst stays responsible for validating everything.
- **Six outputs:** requirement analysis (needs, ambiguities, assumptions, risks), a user story, Given/When/Then acceptance criteria with positive and negative scenarios, a test-case table, clarification questions, and a quality check with review notes.
- **Rules:** don't fabricate requirements, don't hide assumptions, prefer clarification over assumption, and keep everything traceable to the original requirement.
- **Prompt Engineering Mode:** analyse and improve prompts using *Prompt → Test → Evaluate → Refine → Test Again → Final Prompt*.

## Example: "Admin users need to reset user passwords securely"

From that one line, the assistant returned a requirement analysis, a user story, **5 acceptance criteria, 4 test cases and 5 clarification questions**. Crucially, it flagged *"securely"* as undefined and marked the reset method *Requires clarification* instead of choosing one.

## How I built it

I described what I wanted to Gemini in Google AI Studio and iterated, debugging like I would with a dev team:

1. **First attempt only echoed the master prompt back.** I clarified the requirement: a working chatbot, not a document. It generated a web app.
2. **The chatbot didn't respond.** Fix: an API-key settings dialog in the sidebar, with errors shown inside the chat instead of failing silently.
3. **A `marked is not defined` error.** Fix: replace the external markdown library with an internal formatter.

The result is a React + TypeScript + Vite app on the Gemini API, with saved sessions, quick templates, dark mode and Markdown export of any analysis.

## Evaluating a prompt like a requirement

I didn't just eyeball the output. I scored it against a checklist on two real requirements (password reset, and online leave applications):

**What it showed:** the assistant is reliable at the core BA job of naming gaps and asking the right questions. But the same three weaknesses showed up in both runs: specifics added to acceptance criteria (a "403 Forbidden" error, audit-log fields), test cases with no matching criterion, and merged output sections. Those are the documented targets for the next prompt revision.

## What I learned

- Writing "do not invent" into a prompt **reduces** invention but doesn't remove it, so a person must always review the output.
- Explicit rules like *mark unknowns "Requires clarification"* make gaps visible, which is exactly what a BA needs.
- A prompt can be tested like a requirement: against a checklist, on the same inputs, before and after a change.
